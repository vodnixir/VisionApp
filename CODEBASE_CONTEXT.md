# Codebase Context — Speed Battle AI (VisionApp)

> Generated by a deep static analysis pass. Purpose: give any future coding session (human or
> AI) a fast, accurate mental model of the architecture, conventions, and design principles
> already in force, so changes stay consistent with the existing codebase instead of drifting
> from it. This file documents what exists; it does not prescribe new work (see `PLAN.md` for
> the live roadmap/backlog, kept separately in Russian by the project owner).

## 1. What this product is

A browser-based (and Capacitor/Android-wrapped) **motion party game**: a phone/tablet camera
tracks 1–4 people in real time with **TensorFlow.js MoveNet MultiPose Lightning**, converts body
movement into game progress, and displays the result on-screen or cast to a TV. The flagship mode
is a **1v1 duel** — two "fighters" fill a progress bar by moving fast (punching, dodging,
footwork); first to 100% (or the higher bar when the round timer expires) wins. Around that core
the app has grown into several modes: co-op boss fights, rhythm/endurance/traffic-light/pose-copy
variants, a 3–4 player free-for-all, a single/duel/squad endless-runner ("Subway-Surfers-with-your-
body"), and a two-phone WebRTC online battle.

Target audience/positioning (see `PLAN.md` §0): families, kids' entertainers, schools/camps. The
phone is the "referee/host console"; a TV is the "show" for the kids via Chromecast/second-screen
casting. Monetization is host-side (Pro unlock), never mid-match friction for children (no energy
system, no forced ads) — see §7.7.

## 2. Tech stack

- **React 19 + TypeScript** on **Vite 8**, **Tailwind CSS 4** (`@tailwindcss/vite`, CSS-var based
  theme tokens, no config file — v4 CSS-first config lives in `src/index.css`).
- **Computer vision**: `@tensorflow/tfjs-core` + `tfjs-backend-webgl` (always) + `tfjs-backend-
  webgpu` (dynamically imported, preferred when available) + `@tensorflow-models/pose-detection`
  running **MoveNet MultiPose Lightning**, model files bundled locally in `public/models/` (fully
  offline-capable — no CDN fetch at runtime).
- **Canvas 2D** for all in-game rendering (video + brackets + HUD + effects) — no WebGL scene
  graph, no DOM overlay for anything that must appear in recordings or on a cast TV.
- **Web Audio API**: all music and SFX are synthesized with oscillators at runtime — zero audio
  asset files, keeps the offline APK small.
- **WebRTC** (raw `RTCPeerConnection`, no signaling server) for the online 1v1 battle and for TV
  casting; STUN always, optional TURN via build-time env vars.
- **Capacitor 8** wraps the web build as a native Android app (`@capacitor/android`, `filesystem`,
  `share`) served from `https://localhost` inside the WebView (secure-context requirement for
  `getUserMedia`).
- **`qrcode`** for the online-battle invite QR. **`lucide-react`** for icons.
- Package manager/scripts: plain npm; `oxlint` for linting (rust-based, fast, minimal custom
  rules); `tsx` running a hand-written Node sanity-test suite as the only test runner
  (`npm test` / `npm run test:cv` → `scripts/cv-sanity.ts`) — there is **no Jest/Vitest**, and no
  component/UI test layer; CV/game-logic purity is what's covered.

## 4. Entry points & routing

### 4.1 `src/main.tsx` — hash-based mini-router

There is **no SPA router library**. `window.location.hash` is read **once at module load**
(non-reactive); every screen's "back" action does `location.hash = '…'; location.reload()` to
switch routes. Checked in this order:

| Hash | Component | Purpose |
|---|---|---|
| `#show` (checked via `isShowPage()`) | `ShowScreen` | TV/cast receiver — no camera, no menus |
| `#online`, `#online?j=<code>` | `OnlineBattleScreen` | Two-phone WebRTC runner race |
| `#group` | `GroupMatchScreen` | 3–4 player free-for-all (duel scoring engine) |
| `#runner-spike` | `RunnerSpikeScreen` | Dev-only gesture-tuning harness |
| `#runner-demo` | `RunnerGameScreen demo` | Auto-played runner, no camera (attract/preview) |
| `#runner` | `RunnerGameScreen` | Real solo/duel/squad runner |
| *(none of the above)* | `App` | The main 1v1 duel — the flagship game |

### 4.2 `App.tsx` — the duel game orchestrator

Composes: `useGameState` (FSM), `usePoseDetection` (CV engine lifecycle), `modes.ts` (mode
math), `sfx`/`music`, `MatchRecorder`/`useMatchClip` (clip pipeline), `ShowCast` (TV output),
`bracket.ts` (tournament flow), `storage.ts`/`session.ts` (persistence). It owns per-frame
scoring in `onFrame()` and match-end bookkeeping in `finishMatch()`. It renders one of the menu
screens or the arena canvas depending on `game.phase`; the camera/canvas element is **always
mounted**, just hidden outside arena phases, and the canvas itself carries the HUD so it is part
of the TV picture and the recorded clip (never a DOM overlay for match-critical content).

## 5. The core game state machine

`src/hooks/useGameState.ts` is a plain `useReducer` FSM. Phases (`src/types.ts`):

```
HOME → ROSTER            (side menu, returns to HOME)
HOME → MATCH_SETUP → CALIBRATION → PLAYING → GAME_OVER → (REMATCH → CALIBRATION | back to HOME/MATCH_SETUP)
HOME → TOURNAMENT → (per-bracket-match) CALIBRATION → PLAYING → GAME_OVER → back to TOURNAMENT
```

`ARENA_PHASES = [CALIBRATION, PLAYING, GAME_OVER]` — the camera engine runs only in these.
`CalibrationPhase = SEARCHING → LOCKING → COUNTDOWN` inside `CALIBRATION`: once both players are
detected, a 3s lock timer starts (`LOCK_DURATION_MS`); reaching it triggers a drift-free
3-2-1 countdown (`src/countdown.ts` pattern: absolute target timestamps, not chained
`setInterval`, so scheduler jitter never compounds).

Reducer actions are guarded by current phase (e.g. `MATCH_START` only fires from `CALIBRATION`),
making illegal transitions no-ops rather than requiring call-site checks everywhere.

## 6. Computer-vision pipeline

This is the most heavily engineered part of the codebase — the README and `PLAN.md`'s "CV-РЕВОРК"
entry (2026-07-09) document a full rewrite. Three files, cleanly separated by responsibility:

- **`cv/engine.ts`** (`PoseEngine` class) — the only file that touches the camera, TFJS, and the
  canvas. Framework-free (no React) so re-renders can never affect it; React talks to it purely
  through `getConfig()` (read live config each frame) and an `onFrame` callback.
- **`cv/tracking.ts`** — 100% pure functions/classes, no DOM/TF references beyond typing. This is
  where the actual "game feel" tuning constants live, each with a comment justifying its value.
- **`cv/draw.ts`** — pure canvas-drawing functions, one HUD/bracket/mask/splash concern each.

### 6.1 Per-frame pipeline (inference frame, not render frame)

1. **Pacing**: the inference loop awaits `requestVideoFrameCallback` (new camera frame available)
   rather than a fixed timer, with a floor of `MIN_INFER_INTERVAL_MS = 25` — avoids wasted
   inference on duplicate frames and battery burn on 120Hz displays.
2. **ROI zoom**: once the expected number of players (`maxPlayers`) are all tracked, inference
   runs on a cropped region around them (`computeRoi`, `ROI_PAD = 0.35` padding) so each body is
   3–4× larger to the model at living-room distances. Every `FULL_SCAN_EVERY = 10`th frame — or
   whenever a tracked box nears the crop edge (`roiTouchesEdge`) — falls back to a full-frame
   scan so someone re-entering frame is never missed. Crop dimensions are quantized to
   `CROP_QUANTUM = 32px` so the WebGL backend doesn't recompile shaders on every ±1px ROI jitter.
3. **`estimatePoses`** — MoveNet, `enableTracking: false, enableSmoothing: false` (deliberately
   off: the ROI crop changes coordinate space between frames, which would corrupt MoveNet's own
   tracker/smoother — identity and smoothing are entirely custom, see below).
4. **Strict filtering** (`selectFighters`) — poses below `POSE_MIN_SCORE = 0.3` dropped, keypoints
   below `KEYPOINT_MIN_SCORE = 0.3` ignored; survivors sorted by bbox area, only the top `N`
   (mode's player count) kept — background bystanders are ignored "for free."
5. **Role assignment** — two strategies depending on `rolesLocked`:
   - **Positional** (`assignRoles`/`assignRolesN`) — sort candidates by on-screen X (accounting
     for mirror mode), leftmost → slot 0. Used during calibration and by the runner/group modes
     (which never lock roles — players keep their own spot in the room).
   - **Sticky/locked** (`matchLockedRoles`, duel only, active from the 3-2-1 countdown onward) —
     candidates are matched to player slots by **proximity + clothing-colour signature**, not
     screen position, so two kids can cross or swap sides mid-match without swapping which one is
     "blue." A lost track can re-bind to a reappearing body within `REBIND_WINDOW_MS = 2500ms` by
     nearest-anchor; beyond that, or with no anchors at all, it falls back to positional.
   - Colour signatures (`sampleSignatures` in `engine.ts`, duel-only) are a 14-bin hue histogram
     of the torso patch (`torsoSignature`), EMA-blended per player (`SIG_TAU_S = 0.4s`) — the
     tie-breaker when two bodies are both plausible candidates for a slot.
6. **`PlayerTracker`** (per slot, one instance per tracked person) — EMA-smooths bbox
   (`BBOX_TAU_S = 0.1s`) and activity speed (`SPEED_TAU_S = 0.25s`) using a **frame-rate-
   independent alpha** (`alphaFromTau = 1 - exp(-dt/tau)`), keeps a persistence window
   (`PERSISTENCE_MS = 600ms`) so a momentary miss doesn't flicker the bracket, and tracks
   `lastBBox`/`lastSeenAtMs` as re-bind memory that survives track expiry.
7. **Motion scoring** (`motionDelta`) — Pythagorean distance traveled per tracked keypoint
   (wrists/elbows/shoulders, weighted 1/0.75/0.5) between consecutive frames, **averaged, not
   summed**, so a keypoint dropping out doesn't cost points; normalized by the body's bounding-box
   diagonal (camera-distance invariant). A `TELEPORT_GUARD = 0.45` discards single-frame jumps
   too large to be real motion (tracking glitches). Result is scaled by `MOTION_DEADZONE = 0.25`
   (idle jitter floor) to `MOTION_VMAX = 1.6` (max score) per second, then EMA-smoothed.
8. **Anti-cheat amplitude gate** (`amplitudeFactor`) — measures how far the more-extended wrist
   reaches from its shoulder as a fraction of bbox height; tucked-in micro-shaking ("score
   farming") is discounted to `×0.15`, full-extension punches/dodges are boosted up to `×1.5`.
9. **Auxiliary per-frame extraction** (always computed when visible, independent of scoring):
   `bodyPosture()` (torso landmarks for the runner's lane/jump/crouch signal), `armPose()` (arm
   segment directions for pose-copy mode), `faceAnchor()` (head center+radius for the privacy
   mask).
10. **Hints** (`computeHints` in engine.ts, duel-only, 2-player concept) — live calibration
    coaching: `tooFar` (bbox height < 28% of frame), `overlap` (IoU > 0.18), `dark` (sampled luma
    < 58, every `LUMA_EVERY=40` frames via a cheap downscaled readback).
11. **Hitmarker particles** — while scoring, a fast strike (`speed ≥ BURST_SPEED=0.7`) spawns a
    neon particle burst at the active wrist, cooldown `90ms`/player, purely cosmetic feedback for
    the TV/clip.

### 6.2 Rendering

`draw()` runs on a separate `requestAnimationFrame` loop, decoupled from inference rate: draws
the (possibly mirrored) video frame, then — only if `drawOverlays` — brackets (`drawBrackets`,
glow scales with speed), name labels, combo badges, face masks, the canvas-based match HUD
(`drawMatchHud`: two panels with progress bars/names, center timer chip, mode-specific banners
for overtime/traffic-light/freeze/pose-copy target), or the victory splash. Everything the TV/clip
needs to show is drawn to canvas — **no DOM overlay is ever part of the recorded picture**.

### 6.3 Backend selection & reliability

WebGPU is tried first (`'gpu' in navigator`), falling back to WebGL; the working choice is cached
in `localStorage['sb.backend.v1']` so later boots skip a known-failed probe. `WEBGL_USE_SHAPES_
UNIFORMS` is set to reduce shader recompiles. A dead camera (`track.ended`) or
`FATAL_FAILURE_STREAK = 45` consecutive `estimatePoses` failures triggers `onFatal` → a real
`ErrorOverlay` instead of a silent freeze.

## 7. Game modes and scoring composition (`src/modes.ts` + `types.ts` + `App.tsx`)

`RoundMode` (`sprint`/`fight`/`marathon`) sets duration/fill-rate pacing but the base game and
most `MatchMode`s now run **endless** (`isEndless()`) — no clock, first to 100% wins; only the
co-op `boss` mode stays time-limited. `modes.ts` is a **pure, deterministic, rng-injectable**
layer: given per-frame speeds it returns `{ fill, burn, comboEligible, events, pose? }` — `App.tsx`
owns all the stateful bits (accumulators, HUD, sfx side effects). This "pure math module + stateful
caller" split is a repeated architectural pattern across the codebase (see `runner/game.ts`,
`online/protocol.ts`'s RNG).

| Mode | Mechanic |
|---|---|
| `classic` | fill = speed × rate × dt; combo-eligible |
| `rhythm` | beat window (`RHYTHM_BPM=105`, ±170ms); landing a beat gives a bonus, missing trickles 15% |
| `endurance` | pace-capped fill (steady beats sprinting); stalling past a 600ms grace burns the bar |
| `traffic` | alternating red/green light; moving on red burns ×1.5, green fill boosted ×1.25 |
| `pose` | copy a rotating target pose (`POSE_LIBRARY`, mirror/handedness-invariant scoring) |
| `boss` (co-op, Pro) | both players fill ONE shared bar; a boss attacks every 8s for growing damage |

Cross-cutting modifiers layered on top in `App.tsx`: **Freeze** (random windows where moving
drains the bar instead of filling it), **Combo/streaks** (continuous movement compounds fill up
to ×2, classic mode only, with a 600ms grace and a freeze-synergy rule), **Handicap** (pre-match
head start, 0/10/20/30%), **Sensitivity** (pre-match fill-rate scalar), **Overtime** (a near-tie at
the buzzer becomes sudden death: first to +5% over their buzzer score wins, capped at 20s).

## 8. Other first-class modes

### 8.1 Group mode (`#group`, `GroupMatchScreen.tsx`)
3–4 player free-for-all, deliberately kept as a **separate screen** so "the polished two-player
duel stays exactly as it was." Reuses the same `usePoseDetection`/`PoseEngine` (via
`maxPlayers`) and the same classic-mode fill formula/constants from `types.ts`, but each player
gets their own vertical bar and roles are never locked (purely positional, left-to-right). Live
bar updates during play are driven **imperatively via DOM refs**, explicitly to avoid per-frame
React re-renders; only the final results screen uses React state.

### 8.2 Runner mode (`#runner*`, "Subway Surfers with your body")
- **`runner/game.ts`** — pure deterministic simulation (rng-injected, same philosophy as
  `modes.ts`): entities travel along a z-axis (spawn far → resolve near `PLAYER_Z=0.88`), 4 types
  (`jump`/`duck`/`block`/`coin`), difficulty ramps over `RAMP_MS=80s` up to `MAX_FACTOR=1.8`.
  Uses a **fixed simulation step** (`SIM_STEP_S=1/60`, frame-time clamped to `MAX_FRAME_S=0.25`)
  driven by a real-time accumulator in the screen components — spawn cadence/approach speed must
  stay tied to wall-clock time regardless of render fps (a documented regression: heavy 3-body
  tracking used to visibly slow the world down under naive dt handling). Spawn is a pure function
  of RNG + elapsed time only (never entity positions), specifically so two phones on the same
  seed in the online battle never diverge.
- **`runner/gestures.ts`** — pure body→gesture classifier, explicitly framed as answering "WHAT
  did the body do" (discrete lane/jump/crouch events) as opposed to the duel's "HOW MUCH did it
  move" (continuous magnitude). Hysteresis on lane switching, EMA + cooldown on jump detection,
  everything normalized by a calibrated neutral stance so camera distance drops out.
- **`runner/useRunnerControl.ts`** — shared hook (calibration + per-frame gesture reading) reused
  by solo runner, online battle, and the dev spike screen; performance-critical path (`handleFrame`)
  is a zero-dependency `useCallback` reading everything through refs since the engine calls it
  ~30–40×/s.
- **`runner/draw.ts`** — pure canvas rendering of the metro-tunnel scene, shared verbatim between
  `RunnerGameScreen` and `OnlineBattleScreen` so both draw an identical world.
- Modes: `solo` (1 body), `duel` (2), `squad` (3) — `runner/modes.ts` maps each to a player count
  fed straight into the CV engine's `maxPlayers`.
- `#runner-demo` runs a deliberately-imperfect auto-bot (`demoBot`) for attract/preview purposes;
  `#runner-spike` is a **dev-only diagnostic harness** (hardcoded Russian UI, unlike every other
  screen which routes through `i18n`) for live-tuning gesture thresholds against a real body.

### 8.3 Online battle (`#online`, two-phone WebRTC)
- **No signaling server** — connection setup is a manual code/QR/link handshake
  (`src/online/protocol.ts`: `packSignal`/`unpackSignal` gzip+base64url-encode the SDP so it fits
  in a scannable QR; the very first offer/answer is deliberately **data-channel only**, since
  adding a camera track ~5.5×s the SDP size past what a QR can hold — camera is attached *after*
  the data channel connects, via `attachCamera()`/`replaceTrack`).
- **`OnlineConnection`** (`online/net.ts`) — raw `RTCPeerConnection` + one ordered `RTCDataChannel`,
  STUN always + optional TURN (env-configured), perfect-negotiation glare handling (guest=polite,
  host=impolite), non-trickle ICE gathering with a settle heuristic (`ICE_SETTLE_MS=700`,
  `ICE_TIMEOUT_MS=8000` hard cap) since browsers rarely report gathering complete promptly, and a
  4s keepalive ping to survive the ICE consent-freshness window on an idle screen.
- Both phones run **identical local sims** seeded by the same `mulberry32(seed)` PRNG
  (`online/protocol.ts`), so obstacles match without transmitting per-obstacle state — only
  throttled (~5Hz) progress heartbeats and a final score are exchanged. It's a **score race**, not
  frame-perfect lockstep (deliberately accepted small drift risk).
- Camera is intentionally not started during the code-exchange phase (backgrounding to paste a
  code kills the camera track on Android); it starts once both sides are ready.

### 8.4 TV casting (`show.ts` + `ShowScreen.tsx`)
Two transports behind one JSON message protocol: **Presentation API** (real Chromecast/Miracast)
or a `window.open` fallback (second window / extended display / HDMI). On top, **WebRTC streams
the live arena canvas+audio** (LAN-only by design, no STUN/TURN) when it connects; otherwise a
~12Hz throttled scoreboard state message drives a canvas-drawn scoreboard on the receiver so the
TV is never blank. Hidden inside the Capacitor APK (WebView has no Presentation API — native Cast
SDK is a deliberately deferred future task per `PLAN.md`).

## 9. Cross-cutting systems

- **Persistence** (`storage.ts`): one localStorage key (`sb.v1`) holding profiles/settings/last-
  players/tournament as one JSON blob; in-memory read cache; **250ms debounced writes** flushed
  eagerly on `pagehide`/hidden. All reads/writes try/catch-wrapped (private-mode/quota safe).
  `session.ts` is a separate, simpler sessionStorage store for "tonight's tally" (resets when the
  app fully restarts, survives a mid-party reload).
- **i18n** (`i18n.ts`): flat dot-namespaced key dictionaries for `en`/`ru`/`es`/`pt`, `en` is the
  type source (`I18nKey = keyof typeof en` — compile-time-checked keys), `{placeholder}`
  substitution, browser-language auto-detect with manual override, `useSyncExternalStore`-backed
  `useI18n()` hook usable outside React too (canvas draw code calls `t()` directly).
- **Theming** (`theme.ts` + `index.css`): three themes (`neon` arcade/Orbitron/glow, `dark`,
  `light` [default]) — DOM styling via CSS custom properties swapped per `[data-theme]`, and a
  **parallel, deliberately separate** `CanvasTheme` object in `theme.ts` for canvas drawing (HUD,
  masks, banners, TV scoreboard) since canvas can't read CSS vars. Same `useSyncExternalStore`
  singleton-store pattern is reused for `layout.ts` (Home-screen layout variant), `i18n.ts`, and
  `audio/music.ts`'s mute state — a repeated idiom worth recognizing rather than reinventing.
- **Recorder/clip pipeline** (`recorder.ts` + `useMatchClip.ts` + `ClipShare.tsx`): captures the
  match canvas via `canvas.captureStream(30)` + `MediaRecorder` (mp4 preferred, webm fallback),
  live-recomposes into a **9:16 portrait** clip (`PortraitComposer`: blurred cover-crop background
  + contain-fit foreground + theme-matched wordmark, its own throttled rAF loop), scores activity
  in ~10Hz buckets to rank highlight windows (`pickHighlights`, target 20s), and can re-cut a
  sub-clip by **replaying it in real time** into a hidden `<video>` (browsers can't trim an
  encoded blob without a transcoder — an explicit, accepted cost). Sharing branches on platform:
  Capacitor writes to cache + native share sheet; web uses `navigator.share`/download fallback.
- **Tournament** (`bracket.ts`): single-elimination, 3–16 entrants, power-of-two bracket with at
  most one bye per first-round match (guarantees no one skips two rounds), immutable updates
  (`structuredClone` before mutating) so `reportWinner()` never mutates its input, a fixed-point
  `resolveByes()` loop to cascade auto-advances.
- **Monetization gating** (`pro.ts`): `PRO_UNLOCKED = true` hardcoded today (billing not wired
  yet — explicit `TODO`), with the boundary already drawn (`PRO_MODES = ['traffic','boss']`,
  `FREE_BRACKET_MAX = 8`) so flipping the flag later is the only change needed.
- **Audio** (`audio/music.ts`, `audio/sfx.ts`): fully synthesized oscillators, no asset files.
  Music uses a lookahead scheduler (`LOOKAHEAD_MS=25`, schedule 0.12s ahead) across three tempo
  tracks sharing an A-minor tonal center; sfx is one method per event, `captureStream()` taps a
  `MediaStreamAudioDestinationNode` so `MatchRecorder` can mix real game sound into shared clips.
- **Wake lock** (`hooks/useWakeLock.ts`): keeps the screen on during a match; re-acquires on
  visibility change since the Wake Lock API auto-releases when a tab is hidden.

## 10. Coding conventions & design principles (the house style)

These are consistent enough across the codebase to be treated as house rules for any future
change:

1. **Pure logic, injected RNG, separate from rendering/state.** `modes.ts`, `runner/game.ts`,
   `runner/gestures.ts`, `cv/tracking.ts`, `bracket.ts`, and `online/protocol.ts`'s `mulberry32`
   are all dependency-free, deterministic pure functions/classes — no DOM, no React, no
   `Math.random()` baked in (rng is a parameter defaulting to `Math.random`). This is what makes
   `scripts/cv-sanity.ts` possible at all: it is the **only** test layer, and it only covers what
   pure modules expose. **New game/scoring logic should follow this pattern and get sanity tests
   added to `cv-sanity.ts`**, not be written inline in a component or hook.
2. **Comments explain WHY, not WHAT — especially the tradeoff or bug being avoided.** Nearly
   every non-obvious constant, workaround, or ordering decision has a comment naming the specific
   failure mode it prevents (ICE settle timing, SDP size math, crop quantization vs. shader
   recompiles, spawn determinism vs. cross-device drift, debounced storage writes). When adding a
   tuning constant, follow this and say *why* that value, not just what it is.
3. **Refs over state on hot paths.** Anything touched every animation/inference frame (engine
   config, runner control signals, WebRTC renegotiation flags, rAF accumulators) is a `useRef`,
   never `useState` — `useState`/React re-renders are reserved for values that should visibly
   gate rendering.
4. **Canvas owns anything that must appear in a recording or on a cast screen.** HUD, brackets,
   masks, banners, victory splash — all drawn on the same canvas as the video, never as a DOM
   overlay, because DOM never appears in `captureStream()` output or on the WebRTC-streamed TV
   picture.
5. **Engine/game classes are framework-free.** `PoseEngine`, `MatchRecorder`, `OnlineConnection`,
   `ShowCast` are plain TS classes with callback props (`onFrame`, `onFatal`, `onState`, …); React
   hooks (`usePoseDetection`, `useMatchClip`) are thin lifecycle wrappers, never the other way
   around. Engines are constructed lazily inside a user-gesture handler (e.g. `start()`), never in
   a bare `useEffect`, specifically so React Strict Mode's double-invoke can't double-open the
   camera.
6. **Immutable updates for shared/persisted structures.** `bracket.ts`'s `reportWinner` clones
   before mutating; reducers return new state objects; nothing mutates a `Tournament`/`GameSettings`
   in place.
7. **Const arrays/objects as pseudo-enums**, typed via `keyof typeof` or literal unions, rather
   than TS `enum` (`ROUND_MODES`, `MATCH_MODES`, `BELTS`, `LANGS`, `THEME_IDS`).
8. **Defensive storage access.** Every `localStorage`/`sessionStorage` touch is wrapped in
   try/catch with a silent, commented fallback (private browsing, quota, unsupported).
9. **Frame-rate-independent timing everywhere in the CV/game layers.** EMA smoothing uses
   `alpha = 1 - exp(-dt/tau)` (a real time-constant, not a fixed per-frame factor); persistence
   windows are in milliseconds, not frame counts — the explicit goal (stated in the README and
   `PLAN.md`) is that the game feels the same on a 15fps budget phone and a 60fps flagship.
10. **Separate "pure presentation" components from "owns state/effects" screens.** `ClipShare`,
    `InstructionCard`, `StatusOverlay`, `online/ui.tsx`'s building blocks, `runner/draw.ts` are
    all stateless/pure and reused across screens; the owning screen (`MatchSetupScreen`,
    `OnlineBattleScreen`, `RunnerGameScreen`) holds all state/effects and passes data down. Small
    one-off subcomponents (`Chip`, `Toggle`, `StatRow`) stay colocated in the screen file rather
    than being extracted prematurely.
11. **No abstraction for its own sake.** The four `useSyncExternalStore` singleton stores
    (theme/lang/layout/music-mute) repeat nearly identical boilerplate rather than sharing a
    generic factory — consistent with the project's general preference for a few duplicated lines
    over a premature shared abstraction. Don't "fix" this without being asked.
12. **Feature isolation via hash routes.** Experimental or parallel-universe features (online
    battle, group mode, runner, the TV receiver, the gesture-tuning spike) live behind their own
    `#hash` route and mount an entirely separate top-level component in `main.tsx`, rather than
    being folded into `App.tsx`'s state machine. This keeps the flagship duel game's FSM from
    growing branches for features that don't share its lifecycle.
13. **One deliberate style exception**: `RunnerSpikeScreen.tsx` hardcodes Russian text instead of
    routing through `i18n` — it is an internal dev tool, not shipped UI. Don't copy this pattern
    into user-facing screens.

## 11. Build, lint, test, deploy

```bash
npm run dev        # vite dev server, plain http (camera works on localhost only)
npm run dev:lan     # https via self-signed cert (@vitejs/plugin-basic-ssl) — phone/TV testing on LAN
npm run build       # tsc -b && vite build
npm run lint        # oxlint (rust-based; rules in .oxlintrc.json)
npm test            # === npm run test:cv → tsx scripts/cv-sanity.ts (pure-logic sanity suite)
npm run preview     # vite preview of the production build
```

- `vite.config.ts`: `base` is `/VisionApp/` under `GHPAGES=true` (CI) and `/` otherwise (local,
  Capacitor); one alias (`@mediapipe/pose` → `src/shims/mediapipe-pose-stub.ts`) because
  `@tensorflow-models/pose-detection` statically imports a BlazePose/MediaPipe symbol this project
  never uses, and the real package breaks the production bundle.
- `.github/workflows/deploy.yml` builds and deploys `dist/` to GitHub Pages on every push to
  `main`; TURN credentials for the online battle are injected as build-time secrets
  (`VITE_TURN_URL/USERNAME/CREDENTIAL`) — without them the build still works, falling back to
  STUN-only (peers on the same network / with permissive NAT still connect).
- `capacitor.config.ts`: `appId com.speedbattle.ai`, `webDir dist`, `androidScheme: 'https'` so
  the WebView is a secure context. Android build/signing steps are documented in `README.md`.
- TS config is split by project references (`tsconfig.app.json` for app code — `es2023`,
  `moduleResolution: bundler`, `noUnusedLocals`/`noUnusedParameters`/`erasableSyntaxOnly`;
  `tsconfig.node.json` for `vite.config.ts`). Neither file sets `"strict": true` explicitly —
  worth checking before assuming full strict-mode guarantees when writing new code.
- There is **no component/UI/integration test layer** — `scripts/cv-sanity.ts` is Node-only pure-
  math coverage. Anything involving the camera, canvas rendering, WebRTC, or Capacitor plumbing
  is manually verified on-device (see the regression checklist at the end of `PLAN.md`). When
  changing CV/game-math code, add or update a case in `cv-sanity.ts`; when changing anything
  camera/UI-visual, plan for manual device verification — it will not be caught by CI.
